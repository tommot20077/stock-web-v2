<objective>
本 Phase 的技術核心：把 `TradingService.createTrade` 改成 **insert-first 的冪等流程**，並實作 D-07 的 payload 比對。

Purpose：judgment §5 要求「duplicate 回既有交易、**不重複更新 holdings**」。現況 `createTrade` 的順序是「先改 holdings，再 insert transaction」，若冪等只依賴 insert 的 `on conflict`，duplicate 進來時 holdings 已經被動過才發現衝突 —— 那是 append-only 帳本上改不回來的錯。

Output：`TradePayloadMatcher`（純函式）、冪等版 `createTrade`、`TradingServiceTest` 的六條新斷言。

**⚠️ 偏離 CONTEXT.md 的明示點（DP-2，必須在 SUMMARY 交代）**：`04-CONTEXT.md` `<code_context>` 給的步驟順序是「holdings → insert → 衝突處理」，本 plan 採 RESEARCH Q1.7 的方案 A：**零 I/O 驗證 → key 快路徑查詢 → 解析資產 → insert（ON CONFLICT DO NOTHING）→ 有列才改 holdings**。兩者滿足同一組不變量，但方案 A 是單一 `@Transactional`、無 Spring self-invocation 陷阱（Pitfall 6）、無中止交易、無 ERROR log 噪音。

**範圍排除（DP-1 (c)）**：不加 `executedAt` 未來時間驗證、不建 time parser、不改既有 `resolveTradeableAsset` / `parseTimestamp` 的實作。
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| HTTP header → service | `Idempotency-Key` 是完全使用者可控的字串，且會永久寫入帳本 |
| service → holdings 表 | 一次意圖只能改一次持倉；重複改動會污染成本基礎且不可逆 |
| service → 錯誤回應 | 例外訊息是使用者可見的輸出面 |
