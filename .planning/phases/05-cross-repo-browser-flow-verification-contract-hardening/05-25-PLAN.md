<merge_order>
**合併須知(D-07 硬切;兩個 PR 內文都要有這段)**

1. **並行鏈與推送時機**:後端鏈 05-13 ~ 05-15 與前端鏈 05-16 ~ 05-24 在兩 repo 的同名分支平行執行,本 plan `depends_on` 保證兩條鏈都完成後才推送。兩條鏈完成前**不得**推送任一 repo 的 Wave 2 分支或開 PR —— 後端 CI 對全分支 push 都會跑 Browser E2E 並 checkout 前端同名分支,提前推後端會拿前端 Wave 1 程式碼對 Wave 2 後端而紅(反之亦然)。
2. **合併前提**:兩 PR 在同一個 head SHA 上 CI 全綠(Task 2 證據),兩邊 Browser E2E 的 log 顯示解析到的對方 ref 是 `claude/epic-curie-lj8alo`;Task 2 取證之後兩邊都沒有新推送。
3. **合併順序:前端 PR 先、後端 PR 緊接**(同一時間窗,中間不做其他合併或推送)。理由:先合前端時,過渡期組合是「新前端 + 舊後端 develop」—— 舊後端回 JSON number,新前端的 strict mapper 會大聲失敗並顯示錯誤態(fail-closed);新前端送出的字串,舊後端的 Jackson 也接受。若先合後端,過渡期是「舊前端 + 新後端」—— 舊前端把字串當 number 用(例如 `+` 變成字串串接),可能無聲顯示錯值(fail-open)。
4. **預期的過渡紅燈**:前端 PR 合併時觸發的前端 develop push run 會 checkout 尚未合併的後端 develop → browser-e2e 紅,屬預期;後端 PR 合併時觸發的後端 develop push run 會 checkout 已更新的前端 develop → 應直接綠;之後重跑前端那個 run → 綠。除此之外的任何紅燈都不是預期,照 Task 3 回報。
5. **中止 / 回滾**:若前端已合併、但後端 PR 無法在同一時間窗合併(衝突、CI 轉紅等),以 revert PR 撤回前端 develop 上的該次合併,讓兩邊 develop 回到一致;不得只保留一邊(D-07:單邊部署 / 單邊回滾會壞)。
</merge_order>
