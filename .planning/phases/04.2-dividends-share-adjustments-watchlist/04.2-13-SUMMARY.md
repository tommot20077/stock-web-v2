## 測試清理（Pitfall 7）

`DatabaseCleaner#cleanUserData` 與 `AuthPersistenceIT#cleanUserData` 現在執行同一段 SQL：

```sql
BEGIN;
SET LOCAL session_replication_role = 'replica';
DELETE FROM watchlist_items;
DELETE FROM watchlists;
DELETE FROM share_adjustments;
DELETE FROM cash_dividends;
DELETE FROM transactions;
DELETE FROM cash_ledger_entries;
DELETE FROM holdings;
DELETE FROM backtest_runs;
DELETE FROM users;
COMMIT;
```

處理方式和既有的 V15 `cash_ledger_entries` 一樣：append-only trigger 用 replica role 停用。兩處都加了繁中註解，說明新增參照 users 的表時必須同步加進來，因為漏加不會報錯、只會殘留資料。

**本機 PostgreSQL 16 實測**（暫時叢集，放在 `/var/tmp`，沒有碰 `/tmp/claude-0`；做完已停機並刪除）：載入真實的 V1、V2、V3、V7–V11、V14–V18（V4/V5/V6/V12/V13 需要 TimescaleDB，略過），每張表都種資料，股利與股數調整各含一筆沖銷列。

| 檢查 | 結果 |
|------|------|
| 對照組：不開 replica 直接 `DELETE FROM cash_dividends` / `share_adjustments` | `ERROR: … is append-only: DELETE is not permitted`（trigger 有效） |
| 對照組：舊清理 SQL（沒有新表）在 replica 下執行 | 不報錯，但留下 `cash_dividends 2 / share_adjustments 2 / watchlists 2 / watchlist_items 4` 筆孤兒列，正是 Pitfall 7 的現象 |
| 新清理 SQL（從 DatabaseCleaner.java 原樣取出） | `DELETE 4, 2, 2, 2, 1, 1, 1, 1, 2`、COMMIT；九張表全部 0 列，assets 仍是 19 筆 |
| 交易結束後的 `session_replication_role` | `origin`（SET LOCAL 已還原） |
| AuthPersistenceIT 的 SQL | 去除縮排後與 DatabaseCleaner 逐字相同（diff 為空） |
