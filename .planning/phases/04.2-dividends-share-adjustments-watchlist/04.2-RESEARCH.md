## Summary

本 phase 有兩條互不相依的工作線,規劃時可完全平行:

1. **股利與股數調整**的關鍵不在「多一種交易類型」,而在**持倉是就地改寫的物化狀態**:`TradingService.createTrade` 依「請求抵達順序」對 `holdings` 套用 `HoldingCalculator.applyBuy/applySell`,**不會依 `executed_at` 重播**[VERIFIED: TradingService.java:149-167]。所以拆股「依事件日持股計算新股數」(D-08)必須從帳本推導事件日起點的持股 `Q_asOf`,再把差額 `ΔQ` 套到目前持倉;沖銷只能撤銷「已記錄的 ΔQ」而不是反向重算。資料模型建議**新開兩張 append-only 表**(`cash_dividends`、`share_adjustments`),不擴充 `transactions`:`transactions` 的語意是「已成交紀錄」(judgment §1),其 CHECK、`TradeDto`、`TRADE_IDEMPOTENCY_KEY_REUSED`、payload 比對都已凍結進前端契約,擴充會牽動 Phase 4 最多測試覆蓋的路徑。代價是 Trades 頁「全部」需要一個新的 UNION 讀取端點 `GET /api/v1/portfolio/activities`。

2. **04.1 已留好的擴充點直接可用**:`DayPnlCalculator.calculate(..., List<ShareAdjustment> adjustments)` 已實作「`Q0 = Q1 − ΣB + ΣS − Σadjustments`」,目前兩個呼叫點都傳 `List.of()`[VERIFIED: PortfolioQueryService.java:565、674];`CashBalanceCalculator` 以「多來源 `CashFlow` list」為輸入,股利只需多加一個來源[VERIFIED: CashBalanceCalculator.java 類別 JavaDoc「04.2 的現金股利只需再多加一個來源」];V15 的通用 `prevent_append_only_mutation()` 可直接給新表用[VERIFIED: V15__cash_ledger_entries.sql:65]。

3. **Watchlist** 是全新的 user-scoped 可變資料(不是帳本)。建議放在 **asset 模組**:它擁有 `assets` 表(item 的 symbol / name 可直接 JOIN,不必擴充 `AssetFacade`)、已依賴 `MarketDataFacade`,且 `AssetQueryService.toDto` 正是「報價卡同一套」的漲跌 / 量縮寫算法——D-19 要求的一致性可以用**同一段程式**保證,GET 只需 1 次 Facade 呼叫。三個前端頁面的 mock store 依賴可完全移除,但 **Markets / Chart 的行情列本身仍來自 `data.ts`**,這兩頁的 `MockDataNotice` 不能拿掉(鐵律 6),只有 Watchlist 頁可以。

4. **D-19「即時價由前端 WS 訂閱更新」的前提不成立**:前端**沒有任何 WebSocket client**(全 `src/` 只有 `Ops.vue` 的示範字串命中 "WebSocket"),而後端每連線上限 10 個訂閱[VERIFIED: MarketWebSocketHandler.java:56 `private static final int MAX_SUBSCRIPTIONS = 10;`],一個清單最多 100 檔。這是本 phase 唯一需要 Yuan 先裁決的範圍衝突(Open Question 1)。

**Primary recommendation:** 後端 V16(`cash_dividends` + `share_adjustments`,重用通用 append-only function + 各自的沖銷驗證 trigger)、V17(`watchlists` + `watchlist_items`);trading 新增 `ShareAdjustmentCalculator` + `HoldingCalculator.applyShareAdjustment` 純函式先以單元測試釘死 D-05 / D-08 範例,`PortfolioQueryService` 接上股利現金流、`dividendIncome` 與今日 `ShareAdjustment`;summary 快取鍵升 `v3`;新端點 `POST /portfolio/dividends`、`POST /portfolio/share-adjustments`、`GET /portfolio/activities`(trading)與 `/watchlists/**`(asset)。前端新增 `holdingEventApi.ts`、`watchlistApi.ts`、`portfolioApi.listActivities`,Positions 新對話框、Trades 新頁籤、星號清單選擇器、Watchlist 頁轉真。

### Q2.2 事件日持股 `Q_asOf`(D-08「依事件日持股計算」)

持倉表只有「目前」值,事件日持股從帳本推:
```sql
-- 交易(transactions;trading 自己的表)
select coalesce(sum(case when type = 'BUY' then quantity when type = 'SELL' then -quantity end), 0)
from transactions where user_id = :userId and asset_id = :assetId and executed_at < :effectiveAt;
-- 既有股數調整(含沖銷,沖銷列乘 −1)
select coalesce(sum(case when reversal_of_id is null then quantity_delta else -quantity_delta end), 0)
from share_adjustments where user_id = :userId and asset_id = :assetId and effective_at < :effectiveAt;
```
`Q_asOf = 兩者相加`。`case` 兩支都寫明(04.1 Pitfall 9 的教訓:未知 type 得 NULL 而非被 else 吞掉)。索引:`idx_transactions_user_asset_executed`(V10 已存在)與上面新建的 `idx_share_adjustments_user_asset_effective`。

**D-06 / D-09「必須有持倉」= `Q_asOf > 0` 且目前持倉存在且 `total_quantity > 0`**,任一不成立 → 409 `TRADE_INSUFFICIENT_HOLDING`(`fields.symbol = "no holding"`)。

- 不採 `VALIDATION_FAILED`:這是「狀態衝突」(同一請求在有持倉時合法),不是輸入格式錯;D-17 指定 `VALIDATION_FAILED` 的只有 watchlist 上限。

### Q2.3 `effective_at` 必須由後端以標的 `TradingDay` 換算

若讓前端把日期轉成「本地午夜」送 instant:台北 10/31 00:00 = 紐約 10/30 12:00,美股的拆股會被算成「10/30 交易日」生效 → `Q_asOf` 切錯、D-10 當日判斷錯。建議:
- API 收 `effectiveDate`(`LocalDate`,ISO `yyyy-MM-dd`)。
- 在 `TradingDay`(stock-common)新增純函式 `public Instant startOf(LocalDate tradingDate)` = `tradingDate.atStartOfDay().plus(startOffset).atZone(zone).toInstant()`——與既有 `dayStart(Instant)` 的回傳式**同一公式** [VERIFIED: TradingDay.java:80-84 `return tradingDate.atStartOfDay().plus(startOffset).atZone(zone).toInstant();`],因此 `startOf(d)` 與 `findDailyQuotes` 的交易日起點逐位元一致。`TradingDayTest` 已存在,加案例即可。

### Q2.4 時序規則(物化持倉下的正確性守門)

| 規則 | 為什麼 | 違反時 |
|---|---|---|
| 新股數調整的 `effective_at` ≥ 該標的現存「未被沖銷」調整的最晚 `effective_at` | 較晚的調整的 ΔQ 是以「不含較早事件」的 `Q_asOf` 算的;插隊補記會讓兩筆都錯 | 400 `VALIDATION_FAILED`,`fields.effectiveDate` |
| 只能沖銷該標的**最晚一筆**未被沖銷的調整 | 同上:撤掉中間一筆,之後各筆的 ΔQ 基準失真 | 409 `SHARE_ADJUSTMENT_NOT_REVERSIBLE` |
| 沖銷後持股必須 > 0 | 歸零會讓剩餘成本憑空消失;為負違反 `ck_holdings_quantity_non_negative` | 409 `TRADE_INSUFFICIENT_HOLDING` |
| (建議,需 Yuan 確認)`POST /trades` 的 `executedAt` 早於該標的最晚調整 `effective_at` 時拒絕 | 拆股已記錄後再補登拆股前的買入,會以「拆前股數 / 價格」加進「拆後持倉」而無任何調整 | 400 `VALIDATION_FAILED`,`fields.executedAt`——**改動 Phase 4 凍結的 `POST /trades` 行為**,見 Open Question 3 |

沖銷的語意是「這個事件從未發生」:撤銷**已記錄的** ΔQ(不重算比例),之後的真實交易(使用者以真實股數輸入)保留不動——這在「記錯一筆不存在的拆股」情境下是正確的。

### Q2.5 寫入流程(比照 `createTrade` 的 insert-first,但先鎖持倉)

```

### Pattern 2:insert-first 冪等 + 沖銷(複製 `CashLedgerService.createEntry`)

### Pattern 3:afterCommit 失效

### Pattern 4:前端三件組 + 不回退 mock

## Common Pitfalls

### Pitfall 1:拆股以目前持倉計算
**What goes wrong:** 補記上個月的 4:1 拆股時,目前持倉已含拆股後買進的股數,全部乘 4。
**Why:** 持倉是物化狀態,不依 `executed_at` 重播 [VERIFIED: TradingService.java:149-167]。
**How to avoid:** `Q_asOf` 由帳本推(Q2.2),ΔQ 套到目前持倉。
**Warning signs:** 單元 / IT 中「拆股前後各有交易」的案例股數不對。

### Pitfall 2:今日損益傳空 `adjustments`
**What goes wrong:** 拆股當日顯示 −119,600 的假性暴跌(Q4.3)。**平倉候選(`:565`)**最容易漏改。
**How to avoid:** 兩個呼叫點都傳 `day.adjustmentsOf(assetId)`;IT / E2E 以 `market_prices` 種「昨日拆前價 + 今日拆後價」。

### Pitfall 3:`effective_at` 用本地午夜
**What goes wrong:** 美股事件被算到前一個紐約交易日。
**How to avoid:** API 收 `LocalDate`,後端 `TradingDay.startOf`(Q2.3)。

### Pitfall 4:斷言配股後 costBasis 恰好 100000
**What goes wrong:** `holdings` 只存 `avg_cost`(scale 8),1050 × 95.23809524 = 100000.000002,`isEqualByComparingTo("100000")` 紅。
**How to avoid:** 斷言 `avgCost = 95.23809524`,costBasis 以 1e-5 容差或斷言「`qty × avgCost` 與原成本差 < 1 個最小單位 × qty」;契約檔註明攤薄後成本有 scale-8 捨入誤差。

### Pitfall 5:沖銷聚合漏乘 −1
**What goes wrong:** 沖銷列與原列值相同(Q1.3 設計),`sum(amount)` 會把沖銷算成「再領一次」。
**How to avoid:** 所有聚合寫 `case when reversal_of_id is null then x else -x end`;單元 / IT 案例:記一筆 → 沖銷 → 現金與股利收入回到 0。

### Pitfall 6:UNION 排序 NULL 浮頂與 tie-breaker
**What goes wrong:** `sort=quantity&direction=desc` 時現金股利(quantity null)排第一頁最上;跨表 `id` 重複導致分頁跳列。
**How to avoid:** 顯式 `NULLS LAST`;tie-breaker `created_at, uuid`。

### Pitfall 7:新 append-only 表讓測試清理失敗或留孤兒
**What goes wrong:** `DatabaseCleaner` 以 `session_replication_role = 'replica'` 逐表 `DELETE`,目前只列 `transactions`、`cash_ledger_entries`、`holdings`、`backtest_runs`、`users` [VERIFIED: e2e/support/DatabaseCleaner.java:32-36];新表沒加進去,E2E 之間殘留資料(FK 檢查被停用,不會報錯,只會讓斷言莫名失準)。`AuthPersistenceIT` 的清理同樣只列 `transactions / holdings / backtest_runs / users`(連 `cash_ledger_entries` 都沒有)。
**How to avoid:** 兩處都依 FK 順序加入 `share_adjustments`、`cash_dividends`、`watchlist_items`、`watchlists`(在 `users` 之前)。

### Pitfall 8:V16 / V17 版號被搶
**What goes wrong:** 平行 plan 各建一個 V16 → `Found more than one migration with version 16`,Spring context 起不來(STATE 地雷 1)。
**How to avoid:** 第一個 wave 就由單一 plan 擁有 V16、另一 plan 擁有 V17,其餘 plan 不得建 migration;動工前 `ls` 確認最高版號。

### Pitfall 9:summary 快取舊形狀
**What goes wrong:** 共用環境部署瞬間讀到 `v2` 舊 summary(沒有 `dividendIncome`、`totalPnl` 不含股利)。
**How to avoid:** 升 `v3`(Q7),`PortfolioCacheTest` 斷言鍵前綴。

### Pitfall 10:Watchlist 頁仍顯示「即時」或假走勢
**What goes wrong:** 副標「即時行情更新」(`Watchlist.vue:7`)與依代號亂數產生的 sparkline(`:133`)在 API mode 是未接後端的可見內容,違反鐵律 6。
**How to avoid:** 依 Open Question 1 結論改文案;API mode 隱藏假走勢或標示。

### Pitfall 11:`Trades.test.ts` 大量紅燈
**What goes wrong:** 52 個案例的 fetch double 以 `url.includes('/trades')` 過濾,換端點後全部 `unexpected fetch`。
**How to avoid:** 新端點參數名與 `/trades` 完全相同(Q5.2),同一個 plan 機械式更新過濾條件;不要改斷言語意。

### Pitfall 12:`*E2E` 在本機跑不了
本機無 Docker daemon(Environment Availability);`*E2E` 繼承容器基底,`-Dtest='!*IT'` 排不掉它們(STATE 地雷 2)。完成宣稱一律引用 CI 的 Integration / E2E / Browser E2E job 結果。

### Pitfall 13:`mvn -pl` 沒帶 `-am`
跨模組改 `stock-common`(`TradingDay`、`ErrorCode`)時,不帶 `-am` 會測到 m2 舊 JAR(STATE 地雷 3)。

// Source: 依 HoldingCalculator.applyBuy 的既有寫法(HoldingCalculator.java:13-40)推導
public Holding applyShareAdjustment(Holding existing, BigDecimal quantityDelta, OffsetDateTime now) {
    if (existing == null || existing.totalQuantity().signum() <= 0) {
        throw new BusinessException(ErrorCode.TRADE_INSUFFICIENT_HOLDING,
            ErrorCode.TRADE_INSUFFICIENT_HOLDING.defaultMessage(), Map.of("symbol", "no holding"));
    }
    BigDecimal nextQuantity = existing.totalQuantity().add(quantityDelta);
    if (nextQuantity.signum() <= 0) {
        // 歸零會讓剩餘成本憑空消失;為負違反 ck_holdings_quantity_non_negative。
        throw new BusinessException(ErrorCode.TRADE_INSUFFICIENT_HOLDING,
            ErrorCode.TRADE_INSUFFICIENT_HOLDING.defaultMessage());
    }
    BigDecimal totalCost = existing.totalQuantity().multiply(existing.avgCost());
    BigDecimal nextAvgCost = totalCost.divide(nextQuantity, MONEY_SCALE, RoundingMode.HALF_UP);
    return new Holding(existing.id(), existing.userId(), existing.assetId(), nextQuantity, nextAvgCost,
        existing.realizedPnl(), existing.version(), now);
}

public static BigDecimal splitDelta(BigDecimal quantityAsOf, int ratioNew, int ratioOld) {
    // DOWN:合股的零股以小數保留(D-08),但不因捨入憑空多出股數。
    BigDecimal next = quantityAsOf.multiply(BigDecimal.valueOf(ratioNew))
        .divide(BigDecimal.valueOf(ratioOld), MONEY_SCALE, RoundingMode.DOWN);
    return next.subtract(quantityAsOf);
}
```
> `BusinessException(ErrorCode, String, Map)` 三參數建構子的存在:`TradingService.resolveTradeableAsset` 已以 `new BusinessException(ErrorCode.ASSET_NOT_FOUND, "Asset is not tradeable", Map.of("symbol", "not tradeable"))` 使用 [VERIFIED: TradingService.java:349-350]。

### W2. 後端改動(D-22)

**現況:兩個常數各自為政**
- 實際執行上限:`SubscriptionManager.MAX_CHANNELS_PER_SESSION = 10`(SubscriptionManager.java:35),於 `subscribe` 的 `if (next.size() >= MAX_CHANNELS_PER_SESSION)`(:88)不分類型。
- WELCOME 告知值:`MarketWebSocketHandler.MAX_SUBSCRIPTIONS = 10`(:56)——**另一個**私有常數,只用於 WELCOME(:401)。兩者目前只是恰好相等。

**建議設計**
1. `SubscriptionManager`:以 `MAX_TICK_CHANNELS_PER_SESSION = 100`、`MAX_KLINE_CHANNELS_PER_SESSION = 10` 取代單一常數;依前綴分類(大小寫不敏感,`regionMatches(true, 0, "tick.", 0, 5)`——與 parser 的 `CASE_INSENSITIVE` 一致,避免 `TICK.X` 繞過計數);在同一個 `writeLock` 內對 `next` 分別計數。被拒 reason 維持 `"SUBSCRIPTION_LIMIT_EXCEEDED"`(既有字串,前端尚無消費者但 bearer client 可能依賴)。
2. `MarketWebSocketHandler.sendWelcome` 改讀 `SubscriptionManager` 的公開常數(單一事實來源),新增欄位 `maxTickSubscriptions: 100`、`maxKlineSubscriptions: 10`。
3. **相容性**:repo 內沒有任何程式讀 `maxSubscriptions`(後端測試只斷言 payload 含 `"WELCOME"`,MarketWebSocketHandlerTest.java:114;前端無 WS client)。建議**保留 `maxSubscriptions` 並固定為 10**(= 較嚴的 kline 上限,舊客戶端照它自我節制仍不會被拒),在 security.md 標為 deprecated;不要改成 110(舊客戶端可能據此送 110 個 kline 而被大量拒絕)。[ASSUMED: 外部 bearer client 是否存在未知]

### W3. 瀏覽器取 ticket 與握手路徑

1. **Ticket 端點**:`POST /api/v1/market/ws/ticket`,class 層 `@PreAuthorize("isAuthenticated()")` [VERIFIED: WsTicketController.java:44、46、85];回應 `{ticket, expiresIn: 30, wsUrl: "/ws/v1/market"}`(:93、WsTicketResponse 欄位 `ticket`/`expiresIn`/`wsUrl`)。ticket = 32 bytes SecureRandom 的 URL-safe Base64(約 43 字元),Redis `ws:ticket:{ticket}` TTL 30 s,握手時 `getAndDelete` 一次性消耗 [VERIFIED: WsTicketService.java:23-24、33、105、133]。
2. **Cookie 驗證可用**:`JwtAuthenticationFilter` 對非 refresh 端點在沒有 `Authorization: Bearer` 時讀 access cookie(transport = cookie)[VERIFIED: SecurityConfig.java:188-193];`BrowserCsrfFilter` 對非 safe method 且 cookie 驗證的請求要求 `X-XSRF-TOKEN` 與 cookie 相符(:314-333)。前端 `apiRequest`(apiClient.ts:328)對 POST 自動帶 CSRF 與 `credentials: "include"`,401 時走既有單次 refresh / replay。**目前沒有任何測試走 cookie + CSRF 取 ticket**:既有 WS E2E 一律以 bearer 取 ticket(AbstractWsE2ETest.java:136-143)→ 需新 IT(W6)。
3. **握手也會驗 cookie(新發現的地雷)**:瀏覽器在同源 WS 握手會自動帶 cookie(cookie `path: ${STOCK_AUTH_COOKIE_PATH:/}`,application.yaml:71);`/ws/v1/market` **不在** `ACCESS_COOKIE_OPTIONAL_PATHS`(SecurityConfig.java:157-163),所以 access cookie 失效時 JWT filter 先回 401(:206-215),即使 ticket 有效握手也失敗。對策:**每次連線前都經 `apiClient` 現取 ticket**(必要時觸發 refresh、換到新 cookie),且 30 s 內完成握手;切到背景後回前景一律重取(D-23 已要求)。
4. **Origin 檢查**:`WsConfig` 以 `stock.cors.allowed-origins`(與 REST 同一份)呼叫 `setAllowedOrigins`(WsConfig.java:52-73);未設定時為 Spring 預設同源限制。預設值只有 `http://localhost:5173`(application.yaml:78),`e2e-browser` profile 為 `4173,5173`(application-e2e-browser.yaml:35)。⇒ 本機以 dev profile 後端 + `npm run preview`(4173)測 WS 會被 403(表現為 1006)。
5. **Vite 代理已備**:`'/ws': { target: 'ws://localhost:8080', ws: true }`,dev 與 preview 共用(vite.config.ts:9-11、22-24),**不需修改**。
6. **前端組 URL**:比照 apiClient「一律同源相對路徑」:`${location.protocol === 'https:' ? 'wss:' : 'ws:'}//${location.host}${wsUrl}?ticket=${encodeURIComponent(ticket)}`(用回應的 `wsUrl`,不寫死路徑);同源因此 cookie、Origin、代理三者一致。

### W8. 新增 Pitfalls 與 Threats

**Pitfalls**
- **P-W1 代號大小寫**:`tick.aapl` 被 accepted 但永遠收不到(W1)。前端以 `AssetDto.symbol` 原樣組 channel,單元測試斷言送出的字串。
- **P-W2 握手同時驗 cookie**:access cookie 失效 → 握手 401(表現為 1006)即使 ticket 有效(W3-3)。每次連線前現取 ticket。
- **P-W3 任一非法 channel 讓整則 SUBSCRIBE 失敗**並累計格式錯誤,10 次 → 4400。組 channel 前以同一正規式自檢。
- **P-W4 PONG 也吃速率配額**;重連風暴 + 大量 debounce 失效會撞 4008。客戶端 token bucket ≤ 5 則 / 秒。
- **P-W5 把 tick `volume` 當當日量**覆寫 `volumeText`。
- **P-W6 FX / 債券列顯示 LIVE**:它們永遠沒有 tick(W4),live 標示只能在實際收到該代號 tick 後出現。
- **P-W7 jsdom 的真 `WebSocket`**:未注入 factory 的測試會嘗試真實連線、不穩定。
- **P-W8 本機 preview(4173)+ dev profile 後端**:Origin 不在白名單(application.yaml:78)→ 403;本機 WS 驗證用 `npm run dev`(5173)或設 `STOCK_CORS_ALLOWED_ORIGINS`。
- **P-W9 兩個上限常數漂移**:WELCOME 的值必須讀 `SubscriptionManager` 常數(W2)。
- **P-W10 `*E2ETest` 跑在 Unit job**:planner 若以為 WS 測試在 E2E job,CI 證據會引錯 job(W6)。

**Threats**
| Pattern | STRIDE | Mitigation |
|---|---|---|
| ticket 出現在 URL query → 代理 / 存取日誌外洩 | Info disclosure | 一次性(`GETDEL`)+ 30 s TTL + 需同時有效 access cookie 與 Origin;後端目前未啟用 Tomcat access log(application*.yaml 無 `accesslog` 設定)、`WsTicketService` 不記 ticket;前端不得 log URL / ticket。瀏覽器 WS 握手是否帶 `Referer` 未在本 session 查證 [ASSUMED],但頁面 URL 本身不含 ticket,Referer 即使送出也不含它 |
