## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] 20 上限在並發下會被突破：改為鎖後另起查詢計數**
- **Found during:** Task 2
- **Issue:** plan / 契約寫「`SELECT … FOR UPDATE` 鎖住全部清單列 → count → insert」。若直接以鎖查詢回傳的列數當計數，READ COMMITTED 下該查詢的快照在等鎖前就已取得：A 持鎖時插入第 20 個並 commit，B 取得鎖後的列數仍是 19，會插入第 21 個。本機 PG16 重現（鎖查詢 1 列、重新計數 2 列）。
- **Fix:** repository 新增 `int countByUser(Long userId)`；`WatchlistService#create` 在 `lockAllForUser` 之後呼叫它計數。單元測試以 InOrder 鎖定順序 ensureDefault → lockAllForUser → countByUser → insertIfNameFree。
- **Files modified:** WatchlistRepository.java、JdbcWatchlistRepository.java、WatchlistService.java、WatchlistServiceTest.java
- **Commit:** `c92db9d`
- **給 04.2-12：** 100 檔上限同理——`findByUuidForUpdate` 鎖清單列後，以另一個查詢 `count(*) from watchlist_items` 計數。

**2. [Rule 1 - Bug] WatchlistNameRequest 不加 `@Size(max = 30)`**
- **Found during:** Task 2
- **Issue:** plan 寫 `@NotBlank @Size(max = 30)` 但同時要求「trim 後再驗」。`@Size` 在 trim 前檢查且以 UTF-16 長度計：`"  " + 30 字 + "  "` 或 30 個 emoji（60 個 UTF-16 單位）這類符合契約的名稱會被誤擋。
- **Fix:** request 只留 `@NotBlank`；長度由 `WatchlistService.normalizeName`（strip 後 1–30 code point，與 PostgreSQL VARCHAR(30) 字元計數一致）判定。兩條路徑失敗都回 400 `VALIDATION_FAILED` `fields.name`，契約外觀不變。
- **Files modified:** WatchlistNameRequest.java、WatchlistService.java
- **Commit:** `c92db9d`

**3. [Rule 2 - Critical] rename 的殘餘並發衝突處理**
- **Found during:** Task 2
- **Issue:** plan 要求「先查同名再更新，避免在交易內 catch 例外」。兩個並發改名搶同一名稱時兩者都通過檢查，後者會撞唯一約束，未處理的 DataIntegrityViolation 會變成 500。
- **Fix:** UPDATE 內以 `NOT EXISTS` 擋已 commit 的同名（一般路徑不觸發例外）；只有殘餘並發才以 `DuplicateKeyException` 轉成 false → 409。catch 之後交易內不再執行任何 SQL，service 隨即丟業務例外回滾。本機 PG16 重現該唯一衝突。
- **Commit:** `c92db9d`

**4. [Rule 2 - Critical] V18 額外的 DB 層兜底約束**
- `ck_watchlists_name_not_blank CHECK (btrim(name) <> '')`（name 為 NOT NULL，CHECK 不會因 NULL 結果被放行）、`ck_watchlist_items_position_positive CHECK (position > 0)`。不改變 plan 規定的表 / 約束名稱。
- **Commit:** `cc10af2`
