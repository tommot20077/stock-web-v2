## Summary

I reviewed the 49 backend files on branch `claude/epic-curie-lj8alo` against `origin/develop`. Scope: migrations V16–V18, the dividend, share-adjustment and activity paths in trading, the watchlist in the asset module, and the WS subscription-limit change in market-data. I checked them against the frozen `trading-portfolio-contract.md` and `watchlist-contract.md`. Threats already closed in `04.2-SECURITY.md` are not re-reported.

Areas traced in depth that held up:
- **Append-only and reversal triggers.** No NULL-in-CHECK holes: `ck_share_adjustments_shape` spells out `IS NOT NULL`, and the reversal triggers use `IS DISTINCT FROM` on nullable ratios.
- **Reversal sign flips.** `netByAsset`, `quantityAsOf`, `listSince` and the activity `reversed`/`reversible` subqueries all flip the sign of reversal rows correctly.
- **Owner scoping.** Every UNION branch, `findByUuid`, `findLatestActive` and `quantityAsOf` filters on the owner.
- **Lock ordering between `createTrade` and share adjustments.** Both take the same holding-row lock before the guard, the `Q_asOf` read and the update. A trade waiting on the lock re-reads `findLatestActive` in a fresh READ COMMITTED statement after it gets the lock, so it cannot slip past the guard.
- **Day P&L Q0 reconstruction.** Today's adjustments are subtracted, and a reversal row inherits the original's `effective_at`, so a late reversal does not show up as a fake jump in today's P&L.

No BLOCKER-level defect was proven. The remaining issues are:
1. Reversal and idempotent replay are hard-blocked once an asset stops being active or tradeable, even though the activity list still offers `reversible = true`.
2. Watchlist add-by-symbol is case-sensitive, unlike every other symbol-taking write endpoint.
3. Watchlist items of delisted (inactive) assets are hidden from the user but still count toward the 100-item cap, and the UI cannot remove them.
4. Out-of-range dates are not bounded in the application and surface as 500 instead of 400.

## Warnings

### WR-01: [BE] Reversal (and idempotent replay) is impossible once the asset becomes inactive or untradeable, but the activity list still says `reversible = true`

**File:** `stock-module-trading/src/main/java/dowob/xyz/stockwebv2/trading/service/DividendService.java:165-169,351-361`; `stock-module-trading/src/main/java/dowob/xyz/stockwebv2/trading/service/ShareAdjustmentService.java:171,183-192,517-529`; `stock-module-trading/src/main/java/dowob/xyz/stockwebv2/trading/repository/JdbcActivityRepository.java:76-77,94-101`

**Issue:** Both write services call `resolveTradeableAsset(request.symbol())` first. They throw 404 `ASSET_NOT_FOUND` when `!asset.active() || !asset.tradeable()`, and this happens before the idempotency fast path and before the reversal branch. `AssetFacadeImpl.findBySymbol` does not filter on `active`, so the summary is returned and then rejected.

The activity query computes `reversible` only from ledger state (not a reversal, not reversed, latest active), so it never considers asset status.

Failure scenarios:
- A user records a dividend or split for `XYZ`. An operator later sets `assets.active = false` (delisting) or `tradeable = false`. The erroneous entry can now never be corrected, because the ledger is append-only and reversal is the only correction path.
- The activity row still has `reversible: true`. The "沖銷這筆" button is shown, and every click returns 404 `ASSET_NOT_FOUND`. This is a visible control that always fails, which goes against the frontend rule against silently broken controls.
- A client whose original POST timed out retries with the same `Idempotency-Key` after the deactivation. It gets 404 instead of the stored record, which breaks the contract's "same key, same payload, returns the existing row" guarantee.

The share-adjustment reversal is affected the same way: `reverse()` is reached only after `resolveTradeableAsset`.

**Fix:** Require an active, tradeable asset only for *new* (non-reversal) records. For reversals and idempotent hits, resolve the asset without the tradeable check and rely on `validateMirrorsOriginal` / `validateReversalRules` (asset must equal the original's):
```java
// DividendService / ShareAdjustmentService
AssetSummary asset = original != null || knownKeyExists
    ? resolveExistingAsset(request.symbol())      // exists, any status
    : resolveTradeableAsset(request.symbol());    // new record: active + tradeable
```
Alternatively, move the `findByIdempotencyKey` fast path ahead of the tradeable check. If you decide to keep the block, also add `a.active and a.tradeable` to `reversible` (that needs a facade lookup in `ActivityQueryService.toDto`, because trading must not JOIN `assets`) and document the restriction in the contract.

### WR-02: [BE] Watchlist add-by-symbol is case-sensitive, unlike all other symbol-taking write endpoints

**File:** `stock-module-asset/src/main/java/dowob/xyz/stockwebv2/asset/service/WatchlistService.java:156-160`; `stock-module-asset/src/main/java/dowob/xyz/stockwebv2/asset/repository/JdbcWatchlistRepository.java:168-174`

**Issue:** `addItem` only `strip()`s the symbol and then runs `select id from assets where symbol = :symbol and active = true`. The trading paths normalize with `symbol.trim().toUpperCase(Locale.ROOT)` before the equally case-sensitive `findBySymbol`: `DividendService.java:355`, `ShareAdjustmentService.java:521` and `ActivityQueryService.java:152`. All seeded symbols are upper case (`AAPL`, `2330.TW`, `USD/TWD`, `BTC`).

Failure scenario: a bearer client, or any frontend path that does not echo `AssetDto.symbol` verbatim, posts `{"symbol":"aapl"}` to `POST /api/v1/watchlists/{id}/items`. It gets 404 `ASSET_NOT_FOUND` / `fields.symbol`. The same string is accepted by `POST /portfolio/dividends`, `POST /portfolio/share-adjustments` and `GET /portfolio/activities?symbol=aapl`. The watchlist contract specifies a plain `symbol` and says nothing about case.

**Fix:**
```java
.map(s -> s.strip().toUpperCase(Locale.ROOT))
```
Apply this in `WatchlistService.addItem`. Add a WebMvc/IT case with a lower-case symbol.

### WR-03: [BE] Items of delisted assets are hidden from the user but still use the 100-item cap, and the UI cannot remove them

**File:** `stock-module-asset/src/main/java/dowob/xyz/stockwebv2/asset/service/WatchlistService.java:165`; `stock-module-asset/src/main/java/dowob/xyz/stockwebv2/asset/repository/JdbcWatchlistRepository.java:190-195` (countItems, no `active` filter) vs `:236-243` and `:283-289` (itemAssetIdsByUuid / itemsByWatchlist, `a.active = true`)

**Issue:** `countItems` counts every stored row, including assets that were later marked `active = false`. The DTO (`itemsByWatchlist`) and the reorder set (`itemAssetIdsByUuid`) both drop inactive assets. The user never sees those rows and never receives their `AssetDto.uuid`, so `DELETE /{id}/items/{assetId}` cannot be called for them from the UI.

Failure scenario: a list holds 100 items and 3 assets are delisted. The UI shows 97 items. Clicking the star on a new asset returns 400 `fields.items` "at most 100 items", and the user cannot free the 3 invisible slots. Reorder also rewrites positions only for active rows, so the hidden rows keep stale `position` values that collide with the new 1..n sequence (V18 deliberately has no unique constraint). If an asset is reactivated, it reappears in an arbitrary place, ordered by `(position, a.id)`.

The repository Javadoc (`WatchlistRepository.java:114`) says counting stored rows is intentional, but the contract only says "清單已有 100 檔 → 400" and gives no way to remove hidden items.

**Fix:** Count only visible items, so the cap matches what the user sees:
```sql
select count(*) from watchlist_items wi join assets a on a.id = wi.asset_id
where wi.watchlist_id = :watchlistId and a.active = true
```
Alternatively, purge inactive rows inside `addItem` / `reorder` while the list row is locked. Either way, update the contract wording.

### WR-04: [BE] No lower bound on `paidAt` / `effectiveDate`, so out-of-range dates return 500 instead of 400

**File:** `stock-module-trading/src/main/java/dowob/xyz/stockwebv2/trading/api/CreateDividendRequest.java:38`; `stock-module-trading/src/main/java/dowob/xyz/stockwebv2/trading/service/DividendService.java:156-160`; `stock-module-trading/src/main/java/dowob/xyz/stockwebv2/trading/api/CreateShareAdjustmentRequest.java:85`; `stock-module-trading/src/main/java/dowob/xyz/stockwebv2/trading/service/ShareAdjustmentService.java:174-179,198`

**Issue:** Both services check only the upper bound ("not more than 5 minutes in the future"). Java `OffsetDateTime` / `LocalDate` accept years down to -999,999,999, and Jackson's ISO parsers accept signed expanded years. PostgreSQL `timestamptz` / `date` stop at 4713 BC.

Failure scenarios:
- `POST /portfolio/dividends` with `"paidAt":"-10000-01-01T00:00:00Z"` passes validation (no holding is required, D-03). It reaches `insertIfAbsent`, the server raises "timestamp out of range", and `GlobalExceptionHandler`'s catch-all `Exception` handler returns 500 `INTERNAL_ERROR` instead of 400 `fields.paidAt`.
- For share adjustments, the same happens at the first `quantityAsOf` query that binds `:effectiveAt`.
- Dates that are in range but absurd, such as year 0001, are stored silently.

The controller audit only catches `BusinessException`, so these failures are not audited either.

**Fix:** Add a sane floor in the service next to the future check and reject below it with the existing field keys:
```java
private static final OffsetDateTime MIN_EVENT_TIME = OffsetDateTime.parse("1900-01-01T00:00:00Z");
if (requestedPaidAt != null && requestedPaidAt.isBefore(MIN_EVENT_TIME)) {
    throw new FieldValidationException("Invalid paidAt", Map.of("paidAt", "must not be before 1900-01-01"));
}
// same for effectiveDate (fields.effectiveDate)
```

### IN-01: [BE] Javadoc wrongly says a uuid unique-constraint violation still throws under `ON CONFLICT DO NOTHING` with no target

**File:** `stock-module-trading/src/main/java/dowob/xyz/stockwebv2/trading/repository/JdbcDividendRepository.java:50-54`; `stock-module-trading/src/main/java/dowob/xyz/stockwebv2/trading/repository/JdbcShareAdjustmentRepository.java:49-51`

**Issue:** In PostgreSQL, `ON CONFLICT DO NOTHING` without a conflict target absorbs violations of *every* unique or exclusion constraint, including `uk_cash_dividends_uuid` and `uk_share_adjustments_uuid`. Only CHECK, FK and trigger errors still throw. If the uuid ever collided, the insert would return zero rows, the key re-read would miss, and the caller would get a misleading `DUPLICATE_RESOURCE` or `*_ALREADY_REVERSED`. The impact is negligible because uuids are random v4, but the documented invariant is wrong.

**Fix:** Correct the comment ("all unique constraints, including uuid, are absorbed"), or narrow the clause to the two intended constraints using two statements or arbiter indexes.

### IN-02: [BE] `SHARE_ADJUSTMENT_NOT_REVERSIBLE` message does not fit the "original is itself a reversal" case

**File:** `stock-common/src/main/java/dowob/xyz/stockwebv2/common/error/ErrorCode.java:67`; `stock-module-trading/src/main/java/dowob/xyz/stockwebv2/trading/service/ShareAdjustmentService.java:298-301`

**Fix:** Use a neutral message, e.g. "Share adjustment cannot be reversed (not the latest, or itself a reversal)". The frozen-literal test in `ErrorCodeTest` will need updating.

### IN-03: [BE] `validateMirrorsOriginal` parses `request.type()` a second time

**Issue:** `create` has already parsed `type` (line 166). `validateMirrorsOriginal` calls `ShareAdjustmentType.fromApiValue(request.type())` again. This is redundant and lets the two parse sites drift apart.

**Fix:** Pass the already-parsed `ShareAdjustmentType` into `reverse(...)` / `validateMirrorsOriginal(...)`.

### IN-04: [BE] A watchlist name made only of non-breaking spaces passes both the app check and the DB check

**File:** `stock-module-asset/src/main/java/dowob/xyz/stockwebv2/asset/service/WatchlistService.java:228-235`; `stock-db-migration/src/main/resources/db/migration/V18__watchlists.sql:333`

**Issue:** `String.strip()` uses `Character.isWhitespace`, which returns false for U+00A0 and U+2007. PostgreSQL `btrim(name)` trims only ASCII spaces. So `{"name":" "}` creates a list whose name looks blank, even though the contract says blank names are rejected. This is low impact.

**Fix:** Also reject names whose code points all satisfy `Character.isSpaceChar` or `Character.isWhitespace`. Optionally extend the CHECK to `btrim(name, E' \t\n\r ')`.

The server pushes `auth_expired`/`token_revoked` and closes with 4001. The client retries once, the ticket request returns 401, and the stream goes to `closed`. The header reads "即時報價已停止" indefinitely, with no control to recover, until a full page reload. The same thing happens when the refresh token expires while the tab is open.
**Fix:** Let a new consumer, or the session becoming authenticated again, revive `closed`. For example:
```ts
function ensureConnected(): void {
  if (disposed || isHidden()) return;
  if (status.value === 'closed') { authRetryUsed = false; backoffAttempt = 0; }
  else if (status.value !== 'idle') return;
  void connect();
}
```
Alternatively, have App.vue call `getRuntimeApiClients().quotes.reconnect()` when `sessionState.status` becomes `authenticated`, and render the `live-quote-reconnect` button for `closed` as well as `replaced`.

### WR-06: [FE] Watchlist page applies out-of-order responses, so a stale GET can overwrite newer state

**File:** `vue-app/src/pages/Watchlist.vue:404-412` (`reloadLists`), `:389-401` (`loadLists`), `:662-693` (`removeItem`), `:544-545` (`submitCreate`), `:717-726` (`reorderLocal`), `:933-935`; `vue-app/src/composables/useQuoteRefresh.ts:42-45`
**Issue:** `reloadLists()` and `loadLists()` assign `lists.value = await …list()` with no request sequence. `canRefresh()` is checked only when the GET starts. It also does not consider in-flight item removals (`removing` is not part of it).

Silent refreshes fire on every WELCOME, i.e. about a second after the page mounts and on every return to the foreground, and every 5 minutes. Overview has the right pattern (`wlSeq`, `Overview.vue` `loadWatchlist`/`refreshWatchlist`); the Watchlist page does not.
**Failure scenarios:**
1. A resync GET is in flight. The user clicks ✕ on X. The DELETE returns first and `replaceList` drops X. The older GET then lands and puts X back, although the server no longer has it.
2. A GET is in flight. The user moves a row: the optimistic `reorderLocal` runs and the 500 ms debounce starts. The GET lands with the server order. `sendReorder()` then reads `lists.value` and PUTs the server's old order, so the user's move is silently reverted.
3. A GET is in flight. The user creates a list, which is appended and becomes active. The GET lands without it, and `ensureActive()` jumps to the first tab. The new list vanishes until the next refresh.

`Markets.vue`/`Chart.vue` `loadLists` (the picker's `retry`) have the same unguarded overwrite against `onListChanged`.
**Fix:**
- Add a monotonically increasing token, bumped by every GET and every mutation, and drop any GET response whose token is no longer current:
  ```ts
  let listsSeq = 0;
  async function reloadLists() {
    const seq = ++listsSeq;
    try { const data = await watchlistApi().list(); if (seq !== listsSeq) return; lists.value = data; … } catch {}
  }
  // in replaceList / submitCreate / reorderLocal / removeItem success: listsSeq++
  ```
- Add `Object.keys(removing).length === 0` to `canRefresh`.

### WR-07: [FE] A pending reorder for one list is dropped when the user reorders another list while a PUT is in flight

**File:** `vue-app/src/pages/Watchlist.vue:728-737` (`scheduleReorderSave`), `:739-745`, `:748-782` (`sendReorder`), `:851-858` (`selectTab`)
**Issue:** The save queue holds one `pendingReorderListId`. When the list changes, `scheduleReorderSave` calls `flushReorderNow()`. That calls `sendReorder()`, which returns immediately while `reorderInFlight` is true. Line 731 then overwrites the pending list id.
**Failure scenario:**
1. The user moves a row in list A. The debounce fires and PUT #1 is in flight.
2. The user moves another row in A, so `pending=A` and a timer is set.
3. The user switches to tab B. `selectTab` flushes: the timer is cleared, `sendReorder` returns because PUT #1 is in flight, and `pending` stays A.
4. The user moves a row in B. `scheduleReorderSave(B)` tries to flush A, which is again a no-op, then sets `pending=B`.
5. PUT #1 resolves: `pending=B` and `reorderTimer` is set, so nothing is re-sent for A. Only B is sent.

A's second order is shown locally but never persisted. The next silent refresh reverts it without any message.
**Fix:** Track pending orders per list, e.g. `const pendingReorders = new Set<string>()`, and drain every pending list after the in-flight request completes. Alternatively, in `scheduleReorderSave`, when `reorderInFlight` is true and the pending list differs, queue the old id instead of overwriting it.

### WR-08: [FE] In Markets' watchlist views, unchecking a list detaches the picker's anchor, so the panel jumps and focus is lost

**File:** `vue-app/src/pages/Markets.vue:276`, `:324`; `vue-app/src/components/WatchlistPicker.vue:411-428`, `:400-403`, `:487-495`
**Issue:** In Markets' "觀察清單" tab (`baseRows = watchedRows`) and the "★" chip (`rows.filter(r => isWatched(r.sym))`), the anchor star button belongs to a row that only exists while the symbol is in some list.
**Failure scenario:** The user opens the picker from a row in the watchlist tab and unchecks the only list containing that symbol. `onListChanged` removes the symbol, the row (and the anchor `<button>`) unmounts, and the `props.lists` watcher calls `reposition()`. `getBoundingClientRect()` on a detached node returns all zeros, so the panel jumps to the top-left corner (16, 16). Closing with Esc or ✕ then runs `props.anchor?.focus()` on a detached element, and focus falls to `<body>`. That is a keyboard and screen-reader regression: focus is not returned to a meaningful place.
**Fix:**
- In `reposition()`, bail out (keep the last position) when `!anchor.isConnected`.
- In `requestClose(true)`, when the anchor is detached, focus a stable fallback, e.g. the table or tab heading, which the page passes as a `fallbackFocus` prop or handles in `closePicker`.

### WR-09: [FE] The default ex-date (local "today") is rejected by the backend for most of the Taipei morning on US or crypto assets

**File:** `vue-app/src/components/HoldingEventDialog.vue:712-714`, `:726-727`, `:1145-1147`
**Issue:**
- The default and `max` of the ex-date are `todayLocalDate()`, the browser-local date.
- The backend computes `effective_at = TradingDay.startOf(effectiveDate)` in the asset's market time zone and rejects values more than 5 minutes in the future with 400 `fields.effectiveDate` (trading-portfolio-contract, 〈生效時間與時序規則〉).
- For Taipei (UTC+8), NY midnight of date D is D 13:00 local (12:00 during US daylight time), and UTC midnight of D (crypto) is D 08:00 local.

**Failure scenario:** A Taiwan user records a US split on the morning of its ex-date (11-05 09:00 Taipei) and submits the prefilled date 11-05. The backend returns 400 `fields.effectiveDate`. The dialog then shows "除權日不可晚於今天…" for a date that is today on the user's own calendar, and the front-end self-check had let it through. Every share adjustment for a US stock recorded in the Taipei morning, which is the product's main audience, hits this.

This matches UI-SPEC §Interaction 1 (U-07, line 499: `max` = local today, default today). The defect is in the spec as well as the code.
**Fix:** Ask for a spec change: default to the asset market's current date (or yesterday), and clamp `max` using `pickedAsset.market`/`assetType` (or the holding's currency as a proxy). Alternatively, show a market-date hint next to the field. Keep the backend as the authority.

### WR-10: [FE] "建立並加入" in the picker can add the wrong symbol if the picker is re-targeted while the create request is in flight

**File:** `vue-app/src/components/WatchlistPicker.vue:317-347` (esp. `:340`), `:473-476`
**Issue:** `submitCreate` reads `props.symbol` after `await watchlist.create(name)`. Meanwhile the open/symbol watcher (`:473-476`) calls `resetCreate()`, which clears `createBusy`, when the symbol changes. The continuation then carries on with the new symbol.
**Failure scenario:** On a slow network in Markets, the user types a new list name for AAPL and submits, then clicks TSLA's star before the POST returns. Mousedown outside closes the picker, and the click reopens it with `symbol=TSLA`. The POST resolves: the list is created and `addItem(created.id, 'TSLA')` runs. The user's new list contains TSLA, not AAPL.
**Fix:** Capture the symbol before the first await and use it throughout:
```ts
const symbol = props.symbol;
…
emit('changed', await watchlist.addItem(created.id, symbol));
```
Alternatively, abort the add when `props.symbol !== symbol` after the create resolves.

### WR-11: [FE] Trades activity list has no stale-response guard (existing pattern, now easier to hit)

**File:** `vue-app/src/pages/Trades.vue:557-587` (`loadTrades`), `:618-627`, `:671-682`
**Issue:** `loadTrades` writes `tradesState.value = { status: 'loaded', data: result }` for whichever request finishes last. There is no sequence token and no abort. This predates the phase, but the phase raised the chip count from 4 to 6 and added more ways to reload:
