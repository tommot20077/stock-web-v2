## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] 加入前先檢查是否已存在，再檢查上限**
- **Found during:** Task 1
- **Issue:** plan 的 interface 只有 `countItems` + `insertItemAtEnd`。若只靠 insert 的 `on conflict` 判斷重複，清單已滿 100 時重複加入同一檔會先撞上限回 400，違反契約「已在清單中 → 原樣回傳（冪等，不報錯）」。
- **Fix:** repository 新增 `boolean containsItem(watchlistId, assetId)`；順序為 鎖列 → 解析 symbol → containsItem → countItems → insert。單元測試 `addItem_alreadyPresent_returnsUnchanged` 以 count = 100 鎖住。
- **Files modified:** WatchlistRepository.java、JdbcWatchlistRepository.java、WatchlistService.java
- **Commit:** `2aef819`

**2. [Rule 1 - Bug] 重排集合用一次查詢的 `Map<UUID, Long>`，且只含 active 資產**
- **Found during:** Task 2
- **Issue:** plan 寫 `List<Long> itemAssetIds(watchlistId)`，搭配送來的 uuid 就得逐個呼叫 `findAssetIdByUuid`（最多 100 次查詢）。而且若集合含 inactive 資產（`itemsByWatchlist` 不會回給前端），前端送來的集合永遠少一個，該清單會永遠 409、無法重排。
- **Fix:** `Map<UUID, Long> itemAssetIdsByUuid(watchlistId)`，一次 JOIN `assets`、`a.active = true`、依 position 排序，與回給前端的 items 一致。
- **Files modified:** WatchlistRepository.java、JdbcWatchlistRepository.java、WatchlistService.java
- **Commit:** `9006ea5`

**3. [Rule 2 - Critical] 100 檔上限採鎖後獨立計數（handoff）**
- 依 04.2-11 handoff：不用鎖查詢的結果計數。單元測試 `addItem_capUsesCountTakenAfterLock` / `addItem_locksThenCountsThenAppends` 以 InOrder 鎖定 `findByUuidForUpdate → countItems → insertItemAtEnd`；IT 13b 驗證並發；本機 PG16 重現過時快照（見上）。
- **Commit:** `8162cd9`（測試）、`2aef819`（實作）

**4. [Rule 2 - Critical] assetIds 內含 null 回 400**
- `["…", null]` 這類輸入若不處理，會在集合比較時被當成「集合不符」回 409，語意錯誤。service 判為 400 `fields.assetIds`（不用 `List<@NotNull UUID>`：那樣 handler 的 fields key 會是 `assetIds[0]`，偏離契約）。
- **Commit:** `9006ea5`
