# Phase 04.1 Plan 26: CI 12 個現金分錄整合測試失敗的根因與修正 Summary

**一行根因：`JdbcCashLedgerRepository#mapEntry` 以 `rs.getLong("reversal_of_id")` + `rs.wasNull()` 讀可為 NULL 的欄位，
`wasNull()` 在建構子引數中被呼叫時，最近讀取的欄位已是 `idempotency_key`，永遠回 false，
於是所有一般分錄的 `reversalOfId` 被讀成 `0L` 而不是 `null`。**

## 症狀（CI run 40092253638，Integration Tests，head fd70856）

Failsafe 184 run、12 failed：`CashEntryApiIT` 11 個、`PortfolioCashAllocationIT` 1 個，全部是 409 取代預期的 200 / 400。
首筆入金、驗證、列表、跨使用者隔離等測試都綠，失敗集中在「讀回已存在的列」之後的路徑：同 key 重送、所有沖銷、併發同 key。

## 根因

`mapEntry` 原本：

```java
long reversalOfId = rs.getLong("reversal_of_id");        // SQL NULL -> 0
return new CashLedgerEntry(..., rs.getString("idempotency_key"),
    rs.wasNull() ? null : reversalOfId);                  // wasNull 反映的是 idempotency_key
```

JDBC 的 `wasNull()` 只回報「最近一次讀取」的那個欄位是否為 NULL。建構子引數依序求值，輪到 `rs.wasNull()` 時
最近讀的是 `idempotency_key`（NOT NULL），所以恆為 false，`reversal_of_id` 的 NULL 被當成真值 `0L`。
**只有「從資料庫讀回」的列受影響**；`insertIfAbsent` 的 `returning` 同樣走 `mapEntry`，但 service 在新建路徑
只用它的 uuid / 金額等欄位，不看 `reversalOfId`，所以「首筆入金」測試是綠的，這也是缺陷藏得住的原因。

兩條下游路徑把 `0L` 當成真值：

1. `CashEntryPayloadMatcher.matches` 的 `Objects.equals(existing.reversalOfId(), requestedReversalOfId)`：
   `equals(0L, null)` 為 false，同 key 同 payload 的重送被判為不同筆，回 409 `CASH_IDEMPOTENCY_KEY_REUSED`。
2. `CashLedgerService#validateReversalRules` 的 `original.reversalOfId() != null`：
   原分錄 `reversalOfId` 為 `0L`，被當成「原分錄本身是沖銷」，回 409 `CASH_ENTRY_NOT_REVERSIBLE`；
   這在金額、方向、幣別檢查之前，所以連應該回 400 欄位錯誤的案例也都拿到 409。

## 四個假設的判定（依證據，不憑直覺）

| 假設 | 判定 | 證據 |
|------|------|------|
| (1) matcher 用 `equals` 比 BigDecimal，或比了不該比的欄位 | 否定 | matcher 用 `compareTo` / `toInstant().equals`，備註不在比對維度；唯一錯的輸入是 `existing.reversalOfId()` |
| (2) `insertIfAbsent` 無 conflict target 回零列，被誤讀成 key 重用 | 否定 | 真實 Postgres 上 `insertIfAbsent` 的首筆與首次沖銷都正常回一列；零列只發生在真衝突 |
| (3) IT fixture 跨測試重用 key / user | 否定 | 每個測試都註冊獨立的 `UUID.randomUUID()` email 使用者，並用 `UUID.randomUUID()` 組成的 key，不存在殘留列；且 `CashEntryApiIT` 的 key 與 `UUID` 皆為本次請求才產生，沒有任何跨測試共用的狀態 |
| (4) service 順序讓冪等 / 載荷檢查先於驗證 | 否定 | 順序與 javadoc 一致，修正 mapper 後順序本身正確（見下方真實 Postgres 結果） |

## 重現與驗證（本機 PostgreSQL 16 + 真實 PgJDBC，用完即刪）

於暫時目錄 initdb，套用 V15（users 以 stub 表代替），以真實 `JdbcCashLedgerRepository` 與 `CashLedgerService`
（`PortfolioCache` 為 Mockito 替身；交易以 `TransactionTemplate` 包住 `createEntry`）重現 IT 的情境。

修正前：`DB 的 reversal_of_id IS NULL = true`，但 `mapped CashLedgerEntry.reversalOfId() = 0`；
同 key 重送 409 `CASH_IDEMPOTENCY_KEY_REUSED`；首次沖銷、重複沖銷、金額/方向/幣別不符一律 409 `CASH_ENTRY_NOT_REVERSIBLE`；
8 條併發同 key：1 個 200 + 7 個 409 `CASH_IDEMPOTENCY_KEY_REUSED`（與 CI 日誌的該測試失敗訊息一致）；
8 條併發雙沖銷：8 個 409、`reversal_of_id` 計數 0（對應 CI 的 `Expected size: 1 but was: 0`）。
DB 端的觸發器、唯一約束與 `ON CONFLICT DO NOTHING` 在修正前後行為相同，不是缺陷所在。

修正後：

| 情境 | 結果 |
|------|------|
| 同 key 同 payload 重送 | 200，同一個 id |
| 首次沖銷 / 同 key 重送該沖銷 | 200，`reversalOfId` 指回原分錄；重送為同一個 id |
| 另一把 key 再沖銷同一筆 | 409 `CASH_ENTRY_ALREADY_REVERSED` |
| 沖銷「沖銷分錄」 | 409 `CASH_ENTRY_NOT_REVERSIBLE` |
| 金額 999 / 方向相同 / 幣別不同 | 400 `VALIDATION_FAILED`，`fields.reversalOfId = must mirror the original entry` |
| 省略 occurredAt 的重送 | 200，同一個 id |
| 8 條併發同 key | 8 個 200，同一個 id，1 列 |
| 8 條併發不同 key 沖銷同一筆 | 1 個 200 + 7 個 409 `CASH_ENTRY_ALREADY_REVERSED`，`reversal_of_id` 計數 1 |
| 以上兩個併發情境連跑 40 輪 | 0 輪異常、0 個 5xx |
| `listEntries` | 原分錄 `reversed=true`、沖銷分錄 `reversalOfId` 指回原分錄 |

## 修正

`JdbcCashLedgerRepository#mapEntry` 改為 `rs.getObject("reversal_of_id", Long.class)`，它對 SQL NULL 直接回 null
（與同 repo 內 `JdbcBacktestRepository` 讀 `strategy_version_id` 的作法一致）。同時把 `mapEntry` 由 private 實例方法改為
package-private static（行為不變，僅為讓單元測試能直接呼叫）。全 repo 唯一的 `wasNull` 用法就是這一處。

## 為什麼先前的測試沒抓到

- `CashLedgerServiceTest` 把 `CashLedgerRepository` 以 Mockito 替身取代，替身回傳的是手寫、reversalOfId 正確為 null 的
  領域物件：JDBC 的 NULL 對應整段不在其中。`CashEntryPayloadMatcherTest` 同理，輸入是手寫 record。
- 先前執行者的 SQL 層檢查驗的是 V15 的觸發器與約束（資料庫端），結果集如何被 Java 讀回不在其中。
- `JdbcCashLedgerRepository` 沒有任何不經容器就能跑的測試；真正能抓到它的整合測試需要 Docker，本環境沒有，
  第一次實際執行是在 CI。
- 缺陷只對「從資料庫讀回的列」生效，而最簡單的首筆入金測試走的是 insert 的 `returning`，結果不被使用。

## 補上的防線

`JdbcCashLedgerRepositoryMapperTest`（5 個，皆為不需容器的單元測試）：一般分錄 NULL 對應 null、沖銷分錄對應原主鍵、
其餘欄位逐一對應、讀回的一般分錄與重送請求被 matcher 判為同一筆，以及結果集替身本身遵守 `wasNull` 只反映最近一次讀取的
JDBC 契約。RED 階段（修正前）兩個核心案例失敗，原因恰為 `expected: null but was: 0L` 與 matcher 判為不同筆；
修正後全部通過。
