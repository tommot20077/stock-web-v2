## Warnings

### WR-01: Base-currency totals use frozen seed FX rates with no staleness signal

**File:** `/home/user/stock-web-v2/stock-module-asset/src/main/java/dowob/xyz/stockwebv2/asset/service/FxRateFacadeImpl.java:180-193`
**Issue:** `currentRates()` reads `fx_rates` and loads `rate_time` into `FxRate`, but nothing downstream uses it. A repo-wide search finds no writer to `fx_rates` other than the V2 seed migration (four rows: USD/TWD 32.418, EUR/USD 1.0832, USD/JPY 156.42, TWD/USD 0.030847). Every cross-currency figure the phase introduces comes from these rows: `totalMarketValue`, `cash`, `totalEquity`, `marketValueInBase` and the allocation weights. Those numbers will drift from reality as rates move. The DTOs and UI carry no "rates as of" field, so the user cannot tell. Failing to convert (D-04) is reported honestly, but a stale conversion is not. The `fxExcludedCount` / `unconvertedCurrencies` mechanism does not cover it.
**Fix:** Pick one of the following.
- Expose the oldest `rate_time` used as an `fxAsOf` field on `PortfolioSummaryDto` and show it next to the base-currency totals.
- Treat rows older than a configured max age as unconvertible, in `FxRates.of`, so they fall into `unconvertedCurrencies`.
- At minimum, record in the phase docs that FX is seed-only until a rate-refresh job exists, and add a note under the base-currency hint in the UI.

### WR-02: One out-of-enum `assets` row turns portfolio and trade endpoints into HTTP 500

**File:** `/home/user/stock-web-v2/stock-module-asset/src/main/java/dowob/xyz/stockwebv2/asset/service/AssetFacadeImpl.java:335-343`
**Issue:** `mapProfile` calls `CurrencyCode.valueOf(rs.getString("currency"))` and `AssetType.valueOf(...)` unguarded. `assets.currency` is `VARCHAR(10) NOT NULL` with no CHECK constraint (V1 line 26), while `CurrencyCode` has only USD/TWD/EUR/JPY. `findProfiles` is now on the hot path of `summary()`, `listHoldings()`, `createTrade()` and `listTrades()`. A single asset row with e.g. `HKD` makes `IllegalArgumentException` escape. Every user who holds or has traded that asset then gets 500 on summary, holdings and trade history. The sibling `FxRateFacadeImpl.toFxRate` already handles the same class of problem defensively (WARN and skip), so the two facades are inconsistent. The code downstream (`PortfolioQueryService` lines 374-378, 402-406) already expects a missing profile and degrades gracefully, so skipping the bad row is safe.
**Fix:**
```java
private Optional<AssetProfile> mapProfileSafely(ResultSet rs) throws SQLException {
    long id = rs.getLong("id");
    try {
        return Optional.of(new AssetProfile(id, rs.getString("symbol"),
            AssetType.valueOf(rs.getString("asset_type")), rs.getString("market"),
            CurrencyCode.valueOf(rs.getString("currency")), rs.getString("sector")));
    } catch (IllegalArgumentException e) {
        log.warn("assets row skipped, unsupported asset_type/currency: id={}", id);
        return Optional.empty();
    }
}
```
Collect the non-empty results into the returned map. Alternatively, add a V16 CHECK on `assets.currency` mirroring the one on `users.base_currency`.

### WR-03: `@Transactional(readOnly = true)` is documented as a shared snapshot, but the default isolation is READ COMMITTED

**File:** `/home/user/stock-web-v2/stock-module-trading/src/main/java/dowob/xyz/stockwebv2/trading/service/PortfolioQueryService.java:337-362`, `/home/user/stock-web-v2/stock-module-trading/src/main/java/dowob/xyz/stockwebv2/trading/service/CashLedgerService.java:276-295`, `/home/user/stock-web-v2/stock-module-trading/src/main/java/dowob/xyz/stockwebv2/trading/repository/JdbcCashLedgerRepository.java:158-172`
**Issue:** The Javadoc says count and list "share the same transaction snapshot". No isolation level is configured anywhere (a search for `isolation` in `src/main` and the yaml files finds nothing), so PostgreSQL runs READ COMMITTED. Under it every statement takes a fresh snapshot, and `readOnly=true` does not change that.
- In `listEntries`, a concurrent insert between the count and the page query makes `totalElements` disagree with `items`, which is exactly what the comment says the annotation prevents.
- In `summary()`, `listHoldingSnapshots`, `listHoldings`, `tradeCashFlowByAsset` and `netByCurrency` are separate statements. A trade or deposit committing between them yields a summary where, for example, `cash` includes the new trade but `holdings` does not. That summary is then written to Redis for 60 s. The after-commit eviction has already run, so the inconsistent value survives until the TTL.

The window is small, but the documentation promises a guarantee the code does not give.
**Fix:** Either set `isolation = Isolation.REPEATABLE_READ` on these read-only methods (PostgreSQL supports it, and only DB reads sit inside the transaction), or correct the comments and accept the drift. If you keep the cache write, consider skipping `writeSummary` when the read happened concurrently with a write, or shortening the TTL.

### WR-04: Cash amount is validated to 8 decimals and up to 1e12 but sent as a JSON number (IEEE-754 double)

**File:** `/home/user/stock-web-v2-front-end/vue-app/src/components/CashEntryDialog.vue:445-449` (validator), `:567-` (submit); `/home/user/stock-web-v2-front-end/vue-app/src/services/cashApi.ts:89`
**Issue:** The validator accepts a value such as `123456789012.12345678` (20 significant digits). `Number(...)` then `JSON.stringify` sends the nearest double, `123456789012.12346`. The backend stores that value, so the ledger holds a different amount from what the user typed, with no error shown. The backend comment on `CreateCashEntryRequest` argues that 1e12 is safe because it is below 2^53, but that argument only covers integers. Combined with 8 fractional digits, anything past about 15-17 significant digits is silently rounded. The same applies to the reversal path (`reversalOf.amount` is already a double read back from JSON).
**Fix:** Either restrict the client validator to at most 15 significant digits in total, or send `amount` as a decimal string. Jackson coerces a JSON string into `BigDecimal` by default, and `@DecimalMin`/`@Digits` still apply. If you go the string route, update the `CreateCashEntryRequest` type and the mock adapter accordingly.

### IN-03: Overview trade loaders have no stale-response guard, unlike `loadSummary`
