## 凍結契約（前端 04.1-11 / 04.1-12 / 04.1-15 依此）

- `AllocationSliceDto(String category, BigDecimal value, BigDecimal weight)`：`category` ∈ `STOCK` / `CRYPTO` / `BOND` / `FX` / `CASH`；`value` 基準幣、scale 8；`weight` 比值 0..1、scale 8。
- `SectorAllocationDto(String sector, BigDecimal value, BigDecimal weight, int holdingCount, BigDecimal unrealizedPnl)`：`sector` 可為 null（前端顯示「未分類」）。
- `PortfolioSummaryDto` 追加 `List<AllocationSliceDto> allocation, List<SectorAllocationDto> sectorAllocation`，位於 `cashBalances` 之後。
- 分母：`allocation` = 可折算持倉市值 + max(現金, 0)；`sectorAllocation` = 可折算持倉市值（不含現金）。分母不為正 → 兩者皆空 list。
- 排序：`allocation` 依 value 降冪、同值依 category 字母升冪；`sectorAllocation` 依 value 降冪、同值依 sector 字母升冪、null 一律最後。

## 開放問題的決定：summary 快取鍵是否升 v3

**決定：不升版，維持 `portfolio:summary:v2:{userId}:{baseCurrency}`，在契約檔「快取與一致性」記錄 60 秒視窗。**

- 理由 1（正確性）：`v2` 鍵由 04.1-05 引入，Phase 04.1 作為單一部署上線，在此之前 Redis 內不存在任何 `v2` summary，所以正式部署不會讀到「舊形狀的 v2 JSON」。視窗只存在於「部署過 04.1 中途版本（例如只有 04.1-05 的 build）的共用環境」，且最長 60 秒。
- 理由 2（成本）：升 v3 需改 `PortfolioCache`（鍵常數、`evict` 兩處）、`PortfolioCacheTest`、`redis-convention.md`，這些都在本 plan 的 `files_modified` 之外；為一個不會在正式環境發生的視窗擴張範圍不划算。
- 視窗期間的行為：Jackson 對缺欄位的 record 以 `null` 讀入，`cashBalances` / `allocation` / `sectorAllocation` 可能是 `null` 而非空陣列，60 秒 TTL 到期後自動恢復。契約檔已明寫「bearer client 對這些欄位仍應容錯 `null`」。
- 若之後確定有共用環境跑過中途版本且在意該視窗：升 v3 是機械性小改（兩處常數 + 測試 + 文件），屆時另開 plan 即可。
