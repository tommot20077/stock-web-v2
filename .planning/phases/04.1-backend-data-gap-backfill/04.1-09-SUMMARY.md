# Phase 04.1 Plan 09: 可用現金推導與 summary 快取失效 Summary

**summary 新增 `cash` / `totalEquity` / `cashBalances`：現金是「入出金淨額 ± 全部交易現金流（標的幣別）」的即時推導值，不存任何餘額欄位；現金項留在 summary 快取內，入出金與沖銷在 commit 之後只失效四把 summary 鍵。**

## 現金推導公式與回傳形狀

- 交易現金流（每標的一個值，SQL 聚合）：`SELL → quantity × price − fee`，`BUY → −(quantity × price + fee)`；`CASE` 兩支明寫、**無兜底分支**，未知 `transactions.type` 的結果為 NULL、`sum` 略過它。不 join `assets`。
- 入出金淨額（每幣別一個值，SQL 聚合）：`DEPOSIT → +amount`，`WITHDRAWAL → −amount`；沖銷分錄是反向分錄，自然抵銷。
- `PortfolioQueryService#summary` 把兩者組成 `List<CashFlow>`（交易流的幣別取自 `findProfiles` 的標的幣別，D-07），交給 04.1-24 的 `CashBalanceCalculator.balances` 依幣別加總（scale 8，負值保留），再逐幣別以目前匯率折成基準幣。
- 新欄位（追加在 `PortfolioSummaryDto` 尾端，凍結的前 13 個欄位未動）：
  - `cashBalances: List<CashBalanceDto{currency, amount}>`：原幣餘額，依 `CurrencyCode` 宣告順序（**USD、TWD、EUR、JPY**），只含出現過的幣別，無紀錄為空 list；可為負（D-08）。
  - `cash`：基準幣合計；換不到匯率的幣別不計入並列入 `unconvertedCurrencies`（原幣餘額仍在 `cashBalances`）。
  - `totalEquity = totalMarketValue + cash`。`roi` 語意不變（`totalPnl / totalCostBasis`，不含現金；單元測試以手算值 0.94403214 鎖定）。
- 不驗證餘額、不擋任何操作（D-01）。

## 開放問題的結論：summary 快取與現金

04.1-06 留下的問題：現金在快取過的 summary 內，入出金（含沖銷）與交易之後如何保證不讀到舊值。

- **決策**：現金項留在快取內，由寫入端在 commit 之後失效；不在快取外另算。
- **交易**：`TradingService` 既有的 `invalidateAfterTrade` 本來就刪持倉鍵 + 四把 summary 鍵，賣出／買入後現金自動隨之失效，本 plan 未改動。
- **入出金與沖銷**：新增 `PortfolioCache#invalidateSummaryAfterCommit(userId)`，與交易同一個 `afterCommit` 樣板（共用私有 `runAfterCommit`），只刪四把 summary 鍵、不刪持倉鍵（分錄不影響持倉估值）。`CashLedgerService#createEntry` 只在 `insertIfAbsent` 實際建立列之後呼叫。沖銷走同一條新建路徑，因此同樣失效。
- **不失效的路徑**（資料未變）：冪等快路徑命中、insert 落空後重讀命中、驗證失敗、原分錄 404、已沖銷、併發落敗。
- **殘餘競態**：讀者在 commit 前讀 DB、於失效之後才寫回快取，最長 60 秒，與交易路徑相同，已接受並寫入 `PortfolioCache` 類別 Javadoc。
- **證明**：單元層——`PortfolioCacheTest` 三條（延後到 afterCommit、無交易立即刪、回滾不刪；皆斷言不刪任何 `portfolio:valuation:` 鍵）、`CashLedgerServiceTest` 五條（新建入金與新建沖銷各呼叫一次；冪等快路徑、insert 落空重讀命中、四種被拒情形皆 `never()`）。端到端層——`PortfolioCashAllocationIT#depositRaisesCashImmediatelyAfterCommit`：先讀一次 summary 建立快取，入金後立即重讀，`cash` 必須由 −32418 變為 17582（CI-only，見下）。
