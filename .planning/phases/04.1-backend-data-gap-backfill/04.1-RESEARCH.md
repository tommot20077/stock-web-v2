#### 基準幣與匯率

#### 可用現金
- **D-06:** 手動現金帳:使用者記入金 / 出金;買入自動扣(數量 × 價格 + 手續費)、賣出自動加(數量 × 價格 − 手續費)。
- **D-07:** 現金**依幣別分開**記餘額(USD 現金、TWD 現金…);交易的現金異動用該標的的幣別。Overview 顯示時再折算基準幣(D-04)。
- **D-08:** 現金**允許為負**,畫面提示(例:「可能少記了入金」)。不擋交易。
- **D-09:** 入金 / 出金 **append-only**,記錯以**沖銷分錄**修正,不可修改 / 刪除(與 `transactions` 一致,DB 層同樣保護)。
- **D-10:** 餘額**一律從分錄即時推導**(入出金合計 ± 全部既有交易),不另存餘額欄位;功能上線前的既有交易也計入(會讓舊資料現金為負,由 D-08 的提示引導補記入金)。
- **D-11:** 入出金 UI:Overview「可用現金」卡片上的「入金 / 出金」按鈕,開一個與下單 ticket 同風格的小對話框;沿用 `Idempotency-Key` 與成功後重讀(Phase 4 D-14 模式)。

#### 今日損益
- **D-12:** 券商標準算法:昨日即持有的部分 `qty × (最新價 − 前收)`;今日買入 `qty × (最新價 − 買價)`;今日賣出 `qty × (賣價 − 前收)`。
- **D-13:** 「今天」= 各檔**自己市場的最近交易日**,即報價卡同一套 `TradingDay` / `MarketDataFacade.findDailyQuotes`(前收 = 交易日起點前最後一筆,與 1D K 線前一根 close 同義)。總額 = 各持倉最近交易日損益的加總(Yahoo / 券商 App 做法)。
- **D-14:** 顯示於 **Overview KPI + 每筆持倉**:summary 回總額,`HoldingDto` 回單檔。
- **D-15:** 只算**價格損益**,一律用目前匯率折算基準幣,API 與畫面明確標示「不含匯差」。欄位命名預留拆分(如 `dayPricePnl`),將來補 `dayFxPnl` 不必改語意。(Yuan 問「好系統要不要給匯差 / 做選項」:專業平台是**拆價格 / 匯兌兩塊並列**而非切換選項;本 phase 先做價格,匯兌列 Deferred。)
- **D-16:** 今日 % 的分母 = **前收時的持倉市值**(今日買入的部位以買入成本計),與報價卡漲跌 % 同義。
- **D-17:** 沒有前收(新標的 / 行情剛開始收集)或沒有行情的持倉:單檔回 `null`,summary 排除並回傳「N 檔未計入」;**不塞 0**(與報價卡「不塞預設價」一致)。

## Summary

本 phase 的四個缺口在後端各有一個「看起來只是加欄位、實際上牽動多處」的核心:

1. **基準幣**不只是改 summary:目前 `TradingService.summary` 對 `marketValue` / `costBasis` / `unrealizedPnl` 直接 `BigDecimal::add`(`TradingService.java:350-355`),`realizedPnl` 由 SQL `sum(realized_pnl)` 跨幣別加總(`JdbcTradingRepository.java:302-312`),**而前端 Positions 的權重以「原幣持倉市值 ÷ summary 總市值」計算**(`Positions.vue:530-535`)——D-05 一旦把 summary 改成基準幣,這個權重會立刻變錯(USD 部位 ÷ TWD 總額 ≈ 3%)。所以 `HoldingDto` 需要一個基準幣市值欄位,且 realized PnL 要改成「逐資產查回再折算」。
2. **跨模組資料**:`AssetSummary` 沒有 `currency` 與 `sector`(`AssetSummary.java:31-39`),`fx_rates` 全 repo 沒有任何讀者,`users.base_currency` 不存在。需要擴充 `AssetFacade`(新方法 + 新 record,避免改 34 處 `new AssetSummary(` 測試)、新增 `FxRateFacade` 與 `UserPreferenceFacade`(介面放 infrastructure,ArchUnit 規則 2 會檢查)。summary 的 cache-miss 路徑因此需要 **4 次批次 Facade 呼叫**,字面上違反「≤ 3 次」規則 → 這是唯一需要 Yuan 裁決的架構點(Q9)。
3. **今日損益**可以完全從 append-only `transactions` + `findDailyQuotes` 的前收即時推導,**不需要日級快照表**。關鍵洞察:D-12 的三段分解在代數上等於 `Q1×L − Q0×C − ΣB×pb + ΣS×ps`(Q0 = 交易日起點時的持股),與賣出的是哪一批股票無關,因此當沖、全數平倉都正確;拆股擴充點(04.2 D-10)也自然落在「Q0 推導時扣掉當日非現金股數變動」。但**今日全數賣出的部位不在 `listHoldings` 裡**(`total_quantity > 0` 過濾,`JdbcTradingRepository.java:294`),summary 的總額必須另外把它們算進來。
4. **現金帳**是全新 append-only 表(V15),比照 `transactions` 的 V8 trigger 與 V11 冪等鍵,但 V8 的 trigger function 訊息寫死 `transactions`,不可重用也不可修改——新寫一個通用 function。餘額 = 入出金 + Σ 交易現金流(依標的幣別,幣別經 `AssetFacade` 取得,不得 JOIN `assets`)。

**Primary recommendation:** 後端分三層落地——(a) migration V14(`users.base_currency`)/ V15(現金帳 + 通用 append-only trigger);(b) 三個 Facade 擴充 / 新增 + 三個 trading domain 純函式(`DayPnlCalculator`、`CashBalanceCalculator`、`AllocationCalculator`)先以單元測試釘死數學;(c) `TradingService.summary` / `listHoldings` 改成「一次批次讀齊 → 純函式計算 → 寫快取(鍵帶版本與基準幣)」;前端以新 adapter `profileApi.ts`、`cashApi.ts` 與擴充的 `portfolioApi.ts` 接上,Overview 四張 KPI + donut、Positions 產業分布 + 今日損益欄 + 權重修正、Settings 幣別欄位轉真。契約檔 `trading-portfolio-contract.md` 的 summary 語意變更是 **one-way door**,需與程式同一個 PR 更新。

### Q5.1 可用的原料

### Q5.2 核心數學:D-12 分解 = 現金流恆等式(與賣出批次無關)

設 Q0 = 交易日起點持股、B_i/pb_i = 今日買入、S_j/ps_j = 今日賣出、Q1 = 目前持股 = Q0 + ΣB − ΣS、L = 最新價、C = 前收。

D-12 三段:`(Q0 − ΣS)×(L − C) + ΣB×(L − pb) + ΣS×(ps − C)`
展開後 = `Q1×L − Q0×C − Σ(B×pb) + Σ(S×ps)`(代數恆等,`(Q0−ΣS)` 為負時也成立)。

**實作意義**:
- 用右式計算,**不需要決定賣出的是昨天的股還是今天買的股**(當沖、買了又全賣都正確)。
- 全數平倉(Q1 = 0)的部位一樣適用 → 這正是 summary 必須涵蓋的「今日賣光」情形(Q5.4)。
- Q0 由 `Q1 − ΣB + ΣS` 反推,**不需要日級快照表**——回答了 todo `2026-07-19-backend-daily-pnl.md` 的「需要日級快照」疑問(CONTEXT Folded Todos 要求由規劃驗證此點)。
- 單元測試應同時斷言「右式」與「D-12 三段」兩種算法對同一組輸入相等(性質測試),把恆等式本身釘住。

**D-16 分母**:`basis = Q0×C + Σ(B×pb)`;`basis = 0` → 比率 `null`。
**D-17**:無行情(quote 缺)→ `null`;`previousClose == null` 且 `Q0 > 0 或 ΣS > 0`(右式需要 C)→ `null`。若 `Q0 = 0 且 ΣS = 0`(今天才首次買入),右式不需要 C,數學上可算——但 D-17 字面是「沒有前收 … 單檔回 null」。**建議照字面回 null**,並列入 Open Questions 讓 Yuan 確認。[ASSUMED: 照字面解讀] **→ 已被 CONTEXT D-26 推翻(2026-10-24):今天首次買入照 D-12 計算,不回 null。**
**手續費**:D-12 公式不含 fee → 今日價格損益**不扣手續費**,契約檔需明寫(與 realized PnL 會扣 fee 的語意不同,`HoldingCalculator.java:50`)。

### Q5.3 「今日成交」的查詢

```sql

from transactions
where user_id = :userId and executed_at >= :since
```
`:since` = 所有相關資產 dayStart 的最小值。`idx_transactions_user_executed ON transactions (user_id, executed_at DESC, id DESC)` 已存在 [VERIFIED: V9__trading_query_indexes.sql],不需新索引。逐資產再以各自 dayStart 過濾(`executed_at >= dayStart`)。

### Q5.4 ⚠️ 今日全數賣出的部位不在 `listHoldings`

### Q5.5 拆股 / 配股擴充點(04.2 D-10)

拆股(比例 r)當日:持股多出 `ΔQ = Q0×(r−1)`,**沒有現金流**。若把 ΔQ 誤算進 Q0 的反推(`Q0 = Q1 − ΣB + ΣS`),Q0 會被高估,`Q0×C` 用拆前價 → 算成暴漲 / 暴跌。

**建議 04.1 的純函式簽章就留這個參數**(04.1 一律傳空 list):
```java

public record ShareAdjustment(BigDecimal quantityDelta) { }   // 04.2 填;04.1 恆為空

public final class DayPnlCalculator {
    /** @return 今日價格損益(原幣)與 D-16 分母;無法計算時 Optional.empty()(D-17) */
    public static Optional<DayPnl> calculate(BigDecimal quantityNow, DailyQuote quote,
                                             List<DayFill> fills, List<ShareAdjustment> adjustments) { ... }
}
```

### Q5.6 總額與匯率

summary `dayPricePnl` = Σ(單檔原幣今日損益 × 目前匯率)(D-15「一律用目前匯率」);比率 = Σ(pnl_base) / Σ(basis_base)。被排除的單檔(D-17)計入 `dayPnlExcludedCount`;換不到匯率的(D-04)計入 `fxExcludedCount`。**全部持倉都被排除時總額回 `null` 而非 0**;使用者完全沒有持倉也沒有今日成交時回 `0`(那是真實的零,不是缺資料)。[ASSUMED: 兩種邊界的區分,建議寫進契約]

## Q8 — `PortfolioCache`:鍵、失效、部署相容

4. **今日損益放進 holding 快取是安全的**:它只依賴該資產的今日成交(該資產有新交易時 `invalidateAfterTrade(userId, assetId)` 已在 afterCommit 刪除)與行情(TTL 60 秒內的價差可接受,與既有 marketValue 一致)。交易日換日最多延遲 60 秒。

### Pattern 1:純函式先行(DDD-Lite as transaction script)
**What:** 數學放在 `domain/` 無狀態類別,service 只負責「批次讀 → 呼叫 → 組 DTO」。
**When:** 今日損益、現金推導、配置、匯率換算全部適用。
**Why:** architecture.md:9 明訂「business rules live in pure calculators (`HoldingCalculator`, `TradePayloadMatcher`)」;純函式可在 `./mvnw test`(無 Docker)完整驗證,IT 只需驗整合。

### Pattern 2:insert-first 冪等(複製 Phase 4)
**What:** `findByIdempotencyKey` → `insert ... on conflict do nothing returning` `.optional()` → 落空重讀 → payload matcher。
**Example:** `TradingService.java:112-175`、`JdbcTradingRepository.java:64-104`。不可在同一交易內 catch 唯一約束例外再重讀(PostgreSQL 交易已中止,`TradingService.java:101-102` 註解)。

### Pattern 3:afterCommit 失效
**Example:** `PortfolioCache.invalidateAfterTrade`(`PortfolioCache.java:106-117`)。新方法沿用,不得在交易內直接刪。

### Pattern 4:前端三件組 + 不回退 mock
**What:** interface + `createHttpXxxApi` + `createMockXxxApi` + `createXxxApi(mode)`,於 `pageApiClients.ts` 註冊;API mode 測試斷言 mock factory 未被呼叫(`api-adapter-wiring.test.ts` 樣板)。

### Anti-Patterns to Avoid
- **在 trading SQL JOIN `assets` 取 currency / sector**:D-21 明令禁止;即使「只多一欄」也不行。
- **summary 呼叫 `listHoldings` 再補資料**:會讓 Facade 呼叫翻倍(listHoldings 一輪 + 補平倉資產一輪)。summary 應自己一次批次讀齊候選資產。
- **前端用 `holding.marketValue / summary.totalMarketValue` 算權重**:D-05 後單位不同(Q1.4)。
- **今日損益缺資料回 0**:D-17 明令回 null。
- **重用 `prevent_transactions_mutation()`**:訊息會寫錯表名;修改 V8 違反 flyway-convention。
- **入出金成功後呼叫 `notifyTradeCreated`**:會把 Positions / Trades 的「新」高亮指到不存在的交易。

## Common Pitfalls

### Pitfall 1:今日全數賣出的部位從今日損益中消失
**What goes wrong:** summary 只加總 `listHoldings` 的單檔今日損益。
**Why:** `listHoldings` 過濾 `total_quantity > 0`(`JdbcTradingRepository.java:294`)。
**How to avoid:** 候選資產含 `last_updated >= now − 7d` 的平倉列(Q5.4);IT:昨天買、今天全賣 → summary `dayPricePnl = qty × (賣價 − 前收)`。
**Warning signs:** 單元測試只有「持有中」案例。

### Pitfall 2:realized PnL 仍跨幣別加總
**What goes wrong:** 只改了 holdings 加總,`sumRealizedPnl` 原封不動。
**How to avoid:** IT:一筆 USD 平倉 + 一筆 TWD 平倉,基準幣 TWD → `realizedPnl = usd×32.418 + twd`。

### Pitfall 3:Positions 權重單位錯亂
見 Q1.4。**Warning signs:** USD 部位權重顯示個位數 %。

### Pitfall 4:快取鍵不含基準幣 → 切換後 60 秒內數字不變
**Why:** user 模組無法失效 trading 的快取。**How to avoid:** 鍵含幣別(Q8)。前端元件測試:切換後重讀,斷言新 `baseCurrency` 顯示。

### Pitfall 5:Q0 反推誤含非現金股數變動(04.2 拆股)
**How to avoid:** 純函式簽章預留 `ShareAdjustment`(Q5.5),04.1 寫一條 Javadoc 說明;04.2 的 plan 必須讀到這條。

### Pitfall 6:JSON 格式錯誤變成 500
**What goes wrong:** `{"amount":"abc"}` 或 enum 欄位傳錯 → `HttpMessageNotReadableException` → catch-all 500 + ERROR log。
**Why:** 該例外不實作 `ErrorResponse` [VERIFIED: javap],`handleUnexpected` 只特判 `ErrorResponse`(`GlobalExceptionHandler.java:134-143`)。
**How to avoid:** 新 request DTO 的列舉欄位用 `String` + service 白名單;金額格式錯誤仍會 500——建議本 phase 在 `GlobalExceptionHandler` 補一個 `HttpMessageNotReadableException → 400 VALIDATION_FAILED`(靜態訊息)的 handler 並附測試(這也修掉 `POST /trades` 的同一問題)。這是共用邊界的錯誤映射變更,不改 shape;planner 可列為獨立小 task。[VERIFIED 為程式碼閱讀結論;未實際送出請求觀察]

### Pitfall 7:V14 / V15 版號被搶
**How to avoid:** 執行時 `git fetch && git ls-tree -r --name-only origin/develop stock-db-migration/src/main/resources/db/migration/ | sort -V | tail -3` 再定號(STATE.md 地雷 1)。

### Pitfall 8:三角換算用反向列而非直接列
**What goes wrong:** TWD→USD 用 1/32.418 而非 seed 的 0.030847,第 6 位以後漂移,斷言 flaky。
**How to avoid:** 演算法順序固定「直接 → 反向 → 經 USD」(Q2.3);測試以 seed 數值寫死期望值。

### Pitfall 9:交易現金流 `case` 的 else 分支吞掉未來的交易類型
見 Q6.4;兩支都寫明。

### Pitfall 10:`*E2E` 類別在本機 `./mvnw test -pl stock-start` 會因無 Docker 失敗
STATE.md 地雷 2:`*E2E` 繼承 `ContainerIT` 但不以 IT 結尾。本機只跑 `-Dtest='ArchitectureRulesTest,EndpointAuthorizationRulesTest,GlobalExceptionHandlerTest'`。

## Code Examples

### `FxRates` 換算(建議形狀)
```java
// 位置:stock-infrastructure/.../infrastructure/fx/FxRates.java(新)
public final class FxRates {
    private static final int DIVIDE_SCALE = 16;
    private final Map<CurrencyCode, Map<CurrencyCode, BigDecimal>> direct;   // from → to → rate

    public Optional<BigDecimal> rate(CurrencyCode from, CurrencyCode to) {
        if (from == to) {
            return Optional.of(BigDecimal.ONE);
        }
        Optional<BigDecimal> single = singleLeg(from, to);
        if (single.isPresent() || from == CurrencyCode.USD || to == CurrencyCode.USD) {
            return single;
        }
        // D-04:沒有直接匯率時經 USD 三角換算
        return singleLeg(from, CurrencyCode.USD)
            .flatMap(a -> singleLeg(CurrencyCode.USD, to).map(a::multiply));
    }

    private Optional<BigDecimal> singleLeg(CurrencyCode from, CurrencyCode to) {
        BigDecimal d = direct.getOrDefault(from, Map.of()).get(to);
        if (d != null) {
            return Optional.of(d);
        }
        BigDecimal inverse = direct.getOrDefault(to, Map.of()).get(from);
        return inverse == null || inverse.signum() == 0
            ? Optional.empty()
            : Optional.of(BigDecimal.ONE.divide(inverse, DIVIDE_SCALE, RoundingMode.HALF_UP));
    }
}
```
